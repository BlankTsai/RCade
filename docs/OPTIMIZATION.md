# 課程後優化與驗證計畫

## 第一階段：卡頓排查

日誌與量測工具已完成，實際試玩比較待執行。

1. 確認編譯器、raylib 版本與原始碼可否重建。
2. 建立可切換的幀耗時統計，避免逐幀輸出干擾量測。
3. 在同機器、同歌曲與相同測試時間，比較原始日誌設定與降低日誌後的結果；記錄環境、重複次數、平均值、p95/p99 與長幀數。
4. 區分測試過程、實際結果與推測，並請作者試玩回報。

## 後續方向

- 同幀多鍵輸入與一致的判定時間。
- 拍點、落下時間、歌曲 offset 與設備延遲的分離。
- 歌曲尾端音符的截止條件。
- 場景更新與繪圖分離、素材生命週期、可重現建置。
- 重試、暫停、設定與完整結算；固定譜面另行討論。

## 每次變更紀錄

- 問題與重現條件。
- 修改範圍及選擇此方法的理由。
- 驗證方式、結果與未驗證事項。
- 作者試玩回饋。
- AI 協作範圍。



## 第一版試玩方式（2026-09-22）

- 一般遊玩：雙擊 Play.cmd。
- 關閉詳細日誌的量測：雙擊 Profile-Quiet.cmd。
- 恢復詳細日誌的量測：雙擊 Profile-Verbose.cmd。
- 每次只玩同一首歌，維持相同顯示、音訊、背景程式條件；兩模式交錯各三次，正常關閉遊戲後才會保存 profiles/ 下 CSV。
- 統計包括 60 FPS 等待時間，平均約 16.7ms 並不代表 CPU 滿載；主要比較 p95/p99 與超過 25/50ms 的幀數。終端顯示模式也需保持一致，不能一組導向檔案、一組顯示主控台。
- 隨機軌道與人工輸入使兩次試玩不能完全相同；此比較是初步診斷，不是嚴格可重現基準測試。
- 原版根目錄 EXE 的編譯器與依賴不明，應使用同一個新版 EXE 的兩種日誌設定隔離日誌變因。
- 未完成實際遊玩量測前，不宣稱卡頓已解決。
